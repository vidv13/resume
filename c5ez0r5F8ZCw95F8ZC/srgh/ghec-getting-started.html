Mental Model · Where you sit

Four nested layers — you own the middle one

Everything on the platform lives inside this hierarchy. Identity and platform-wide rules are set above you; the day-to-day work happens below.

Layer 1 Enterprise Identity, SSO, SCIM, licensing — set by enterprise owners
Layer 2 Organization Teams, repos, org policies — this is your domain
Layer 3 Teams Groups that hold access — mirrored from Entra groups
Layer 4 Repositories The actual code, issues, and pull requests
Identity · What EMU changes

These aren't ordinary GitHub accounts

Enterprise Managed Users trade openness for control. Knowing the guardrails up front saves you from confused support tickets later.

Standard GitHub

  • People sign up themselves, pick any username
  • Public repos, forks, and gists allowed
  • Invite anyone as an outside collaborator
  • One account roams the whole internet

Your enterprise (EMU)

  • Accounts are provisioned from Entra via SCIM
  • Usernames are fixed: alex_yourco
  • No public repos, no forks out, no outside collaborators
  • Accounts only see your enterprise — a walled garden
Deprovisioning in Entra suspends the GitHub account — offboarding is automatic, not a manual step.
Roles · Enterprise owner vs. you

Know your lane — and your ceiling

Some controls simply aren't yours to change; the enterprise owner sets them once for everyone. Escalate those instead of hunting for a setting that isn't there.

Above you — enterprise owner

Sets the platform

SSO & SCIM with Entra · enterprise-wide policies · license & Copilot allocation · which orgs exist · security defaults every org inherits.

Your seat — organization owner

Runs the org

Create teams & repos · assign repo roles · branch protection rulesets · org-level policies · enable security features · manage the org profile.

Rule of thumb: if it's about who a person is, it's enterprise + Entra. If it's about what a repo does, it's you.

The EMU catch

Create the GitHub team first, then connect it to an Entra security group. Nested groups and Microsoft 365 groups won't sync.

Base permission

Set the org's default member access to None or Read — then grant more deliberately through teams.

Access · Teams & repository roles

Grant access to teams, never to people

Five built-in repository roles, from look-but-don't-touch to full control. Assign them to teams so access follows the org chart on its own.

Level 1

Read

Clone, open issues, comment.

Level 2

Triage

Manage issues & PRs, no code.

Level 3

Write

Push branches, open PRs. Most devs live here.

Level 4

Maintain

Manage the repo, minus sensitive settings.

Level 5

Admin

Everything, incl. delete. Keep it rare.

Nested teams inherit

A parent team's access flows to child teams. Model Engineering → Platform → Payments and grant broadly at the top.

Least privilege wins

Start people on Read or Write. Admin should be a two-person job, not a default.

Workflow · Repositories 101

A repository is one project's home

Code, history, issues, pull requests, and settings all live together. A few defaults are worth getting right on day one.

Visibility

Under EMU it's Private or Internal only. Internal = visible to the whole enterprise; great for shared libraries. Public is off.

Default branch

main is the source of truth. Everything ships by merging into it — so it's the branch you'll protect.

Starter files

A README, a .gitignore, and a license (or a template repo) save every new project the same setup tax.

Tip: turn your standard setup into a template repository so new repos start compliant instead of being fixed later.
Workflow · The pull request loop

Every change takes the same path

Nobody edits main directly. Work happens on a branch and comes home through a reviewed pull request — that loop is the collaboration model.

Governance · Protect main

Rulesets are your quality gate

A ruleset on main turns "please review" into an enforced contract. Set it once per repo (or across repos) and the platform holds the line.

  • Require a pull request before merging — no direct pushes to main.
  • Require approvals (one or two reviewers) and dismiss stale ones when new commits land.
  • Require status checks — tests and scans must pass before the button lights up.
  • Block force-pushes and require linear history to keep the record clean.
  • Add a CODEOWNERS file to auto-request the right reviewers for each path.
Governance · Security essentials

Turn on the safety net

A few toggles catch the most common mistakes automatically. Some are free platform features; the deeper scanning needs GitHub Advanced Security to be licensed for your enterprise.

Sign-in & MFA

Handled for you: authentication and multi-factor happen in Entra ID at sign-in. There's no separate GitHub password to enforce.

Secret scanning

Turn on push protection so a leaked API key or token is blocked before it ever reaches the repo.

Dependabot

Automatic alerts and PRs for vulnerable dependencies — patch known CVEs without hunting for them.

Code scanning

Static analysis (CodeQL) flags injection, unsafe patterns, and more right inside the pull request.

Governance · Org-level policies you set

Set the guardrails once

These org settings decide what members can and can't do by default. Tighten them early — loosening later is far easier than clawing access back.

Repository creation

Decide who can create repos and which visibilities are allowed — keep it to Private/Internal.

Default permission

The baseline every member gets org-wide. None or Read is the safe floor.

Deletion & transfer

Restrict who can delete or transfer repos so nothing important vanishes by accident.

Apps & OAuth

Require approval for third-party apps and GitHub Apps before they touch org data.

Actions policy

Choose which Actions/workflows may run — allow-list trusted publishers.

Default rulesets

Apply branch protection across every repo at once, not one at a time.

Some of these may be locked by an enterprise-wide policy — a greyed-out setting means it's decided above your level.
