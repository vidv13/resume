Platform
on Mission LZ

An internal application platform that lands inside your existing Mission Landing Zone hub-and-spoke topology, built on the principles of MinimumCD.org. Internal-only by default; public exposure is an explicit, exceptional path.

What changed in this revision: the platform is no longer a standalone greenfield design. It is scoped as workload tiers inside MLZ, which means forced-tunnel egress through the hub firewall, private endpoints on every PaaS service, a private AKS API server, self-hosted build agents, and internal load balancer ingress. Azure Front Door has been removed from the default path and replaced with an internal ingress model plus a documented external exception.
Where the Platform Lives in MLZ

Mission Landing Zone deploys hub-and-spoke networking separated by tiers: T0 for identity and authorization, T1 for infrastructure operations, T2 for DevSecOps and shared services, and multiple T3 spokes for workloads. Your platform is not a new landing zone — it slots into T2 and T3. Purple below already exists; blue is what you build.

HUBNetwork Hub
Azure Firewall Premium MLZ deploys this MLZ configures the firewall as the default route for every tier — a 0.0.0.0/0 UDR pointing at the firewall's private IP. Premium is the MLZ default because its IDPS capability is what satisfies the SCCA VDSS requirement; Standard is selectable via the firewallSkuTier parameter if you don't need IDPS. Your AKS egress design has to be built around this, not alongside it.
T0Identity & Authorization
Entra ID + optional ADDS exists App registrations live in the existing Entra tenant. MLZ optionally deploys domain controllers here if deployActiveDirectoryDomainServices was enabled. Nothing for the platform to build — you consume it.
T1Infrastructure Operations
Log Analytics Workspace reuse, don't rebuild MLZ already stands up a central Log Analytics workspace in the operations spoke, and its default firewall rule collection explicitly permits spoke traffic to reach it on port 443. Do not create a second workspace. Point Container Insights and Application Insights at the existing one. Your cost here is ingestion volume, not the workspace itself.
T2DevSecOps & Shared Services
Platform shared services you build Azure Container Registry (Premium, private endpoint), the self-hosted Azure DevOps agent pool, the platform Bicep/Helm repo, and the shared App Configuration stores. MLZ literally names this tier "DevSecOps," so it is exactly where the SCCA design expects your pipeline infrastructure to sit.
T3Workload — Non-Prod
AKS cluster: dev + staging namespaces you build One private AKS cluster serving both dev and staging. Separate spoke from production, so a non-prod mistake cannot reach prod data or prod identity. Key Vaults for dev and staging plus their private endpoints live here.
T3Workload — Production
AKS cluster: prod namespace you build Dedicated spoke, typically a dedicated subscription, and a dedicated private AKS cluster. The prod Key Vault is reachable only by this cluster's workload identity. This separation is what lets you have both a genuine rollback capability and a staging environment you can trust.
Single Cluster or Two?

My earlier design put dev, staging, and prod in one cluster as three namespaces. Under MLZ that's the wrong call, and it's worth being explicit about why the recommendation changed rather than quietly swapping it.

Previous recommendation

One cluster, three namespaces
Cheaper and simpler. Namespace RBAC gives logical isolation. Perfectly reasonable for a standalone commercial-Azure deployment with no compliance boundary in play.
Why it no longer fits: MLZ expects workloads in separate T3 spokes, usually separate subscriptions. A single cluster spanning what should be two isolation boundaries undercuts the separation-of-duties model SCCA is built on, and it puts every dev experiment inside the prod blast radius.

Revised recommendation

Two clusters, two T3 spokes
One non-prod cluster hosting dev and staging namespaces, one prod cluster, in separate spokes. Costs roughly one extra control plane (~$73/mo) plus a small system node pool. In exchange: a real isolation boundary, an independent upgrade cadence so AKS upgrades get tested in non-prod first, and a separation of duties that maps cleanly onto MLZ's tier model.
Dev and staging share a cluster because they share a trust level. Staging still mirrors prod configuration — it just doesn't need its own subscription to do that.

Key Design Decisions

Revised for the MLZ context.

Orchestration

AKS — private clusters
Still the right fit for a mixed C#/Python/JS portfolio, and MLZ explicitly names containerized applications as a target workload. Private API server, userDefinedRouting egress, Azure CNI, and workload identity all become mandatory rather than optional.
Alt: Azure Container Apps — simpler, but private networking and forced-tunnel support is more constrained.

Ingress — the 90%

Internal load balancer
Since nearly all apps are internal-only, the default is an internal-facing NGINX controller behind an ILB with a private DNS zone. No public IP, no WAF, no Front Door in the default path. Cheaper, and a far easier story in an accreditation conversation.
Removed from the previous design: Azure Front Door as the standard prod ingress.

Ingress — the 10%

App Gateway WAF v2, per exception
For the rare externally-facing app, an Application Gateway with WAF v2 fronts a private backend. Inspection stays inside your own VNet and boundary rather than at a global edge, which is a much simpler SCCA story than Front Door. Treat each exposure as a reviewed exception with a named owner.
Alt: Front Door Premium with Private Link origin — viable, and worth it only if you genuinely need global edge distribution.

Build agents

Self-hosted VMSS agents in T2
A private API server and private-endpoint ACR are unreachable from Microsoft-hosted agents. VMSS-backed pools scale to zero when idle, keeping cost modest, and they inherit the hub firewall egress path like everything else in the estate.
Budget roughly $60–120/mo depending on build volume and how aggressively you scale down.

Secrets

Key Vault + CSI + Workload Identity
Unchanged in shape, with two additions: public network access disabled on every vault, and a private endpoint per vault per spoke. Workload Identity federation means there are no service principal secrets to rotate anywhere in the system.
Private endpoints add roughly $7/mo each plus data processing — individually small, collectively a real line.

Policy compliance

Inherit MLZ's Azure Policy
MLZ applies Azure Policy initiatives including a NIST 800-53 audit set, and your platform Bicep will be evaluated against them. Run what-if deployments against the policy assignments early — discovering a deny policy after the Helm charts are written makes for a bad week.
MLZ's own docs are careful to say the technologies in use can be compliant, not that your workloads are. App-level compliance stays your work.
Networking & Ingress

The area that changed most from the original design. Internal-first by default, with a deliberate documented path for the exceptions.

🔒

Forced Tunnel Egress

MLZ constraint — non-negotiable

MLZ sets a 0.0.0.0/0 route on every tier pointing at the hub firewall as a virtual appliance. Create AKS with outboundType: userDefinedRouting so it doesn't provision a competing public egress path. Then allow the AKS required endpoints on the firewall — the AzureKubernetesService FQDN tag covers the bulk, plus rules for ACR, Entra endpoints, and any package feeds your builds need.

🔑

Private API Server

AKS private cluster

The Kubernetes API server gets a private IP and a private DNS zone. Developers reach it through the corporate network, never from the internet. This is what makes "the pipeline is the only deployment path" enforceable at the network layer rather than by policy alone.

🏠

Internal Ingress — default

90% of your apps

NGINX ingress with the internal load balancer annotation, backed by a private DNS zone linked to each spoke VNet. Apps resolve to private IPs, reachable over your existing ExpressRoute or VPN. cert-manager issues certificates from your internal CA. No public surface at all.

🌐

External Exception Path

10% — reviewed case by case

Application Gateway with WAF v2 in a DMZ subnet, backend pool pointing at the internal ingress. Roughly $0.443 per gateway-hour plus a capacity-unit charge — call it $330–420/mo for the first gateway. One gateway hosts multiple external apps via listeners, so this is a per-gateway cost, not per-app.

🔌

Private Endpoints Everywhere

ACR, Key Vault, App Config

Every PaaS dependency gets a private endpoint with public network access disabled. Budget roughly $7/mo per endpoint plus data processing. With one ACR, three Key Vaults, and three App Config stores across two spokes you're looking at eight to ten endpoints.

🚪

Default Outbound Access is Gone

Changed 31 March 2026

Microsoft retired implicit default outbound access. Every workload now needs an explicit egress path — firewall, NAT Gateway, or load balancer outbound rules. Under MLZ the hub firewall is that path, so you're covered by design, but it has to be a conscious configuration rather than something inherited for free.

MinimumCD Principles

The principles from minimumcd.org haven't changed. What changed is that MLZ makes some of them easier to enforce and others harder to achieve — worth knowing which is which before you start.

🌿

Trunk-Based Development

Required for CI

Everyone integrates to main at least daily. Short-lived branches merged within a day or two. Branch policies enforce it. Unaffected by MLZ — this is a team practice, not an infrastructure one.

🔴

Red Build = Full Stop

CI discipline

A failed pipeline blocks the deployment gate to every environment, and fixing it is the highest priority work on the board. No bypasses. Enforced in the shared pipeline template so individual apps cannot opt out.

📦

Immutable Artifacts

Build once, promote by digest

Images built exactly once, tagged by git SHA, with ACR tag immutability enabled. Promote by digest rather than tag so there's no ambiguity about what shipped. The artifact that passed staging is what runs in prod.

🚦

Pipeline is the Only Path

MLZ makes this EASIER

With a private API server, developers physically cannot kubectl apply from a laptop over the internet. Combine that with namespace RBAC scoped to the pipeline's workload identity and the constraint is enforced by network topology rather than by policy documents and good intentions.

🪞

Production-Like Staging

MLZ makes this HARDER

Staging now sits in a different spoke and subscription from prod, with different firewall rule scope and different private endpoints. Real parity takes deliberate work: the same Bicep modules parameterised per environment, the same secret names, the same ingress class, the same policy assignments. Watch the networking layer specifically — that's where the differences hide.

⏪

Rollback on Demand

Verified, not assumed

helm rollback against an immutable prior digest. Because promotion is by digest, the previous version is guaranteed still to exist in ACR. Test this during platform setup and re-test quarterly — an untested rollback is a hope, not a capability.

🧪

Automated Quality Gates

Beyond minimum

The pipeline decides releasability. Tests, coverage thresholds, linting, and image vulnerability scanning run automatically, and a failure is a failed build. Manual approval on the prod gate is a business decision, not a quality check.

✂️

Small, Frequent Changes

Beyond minimum

Stories decomposed to one or two days. Feature flags via App Configuration let incomplete work merge to trunk without reaching users. Small changes are easier to review, test, and reverse.

📈

Improve the Pipeline Itself

Beyond minimum

Track build duration, deployment frequency, lead time, and MTTR. In a private topology build times get worse before they get better — self-hosted agent cold starts are a real tax. Treat that as a bug to fix, not a fact of life.
